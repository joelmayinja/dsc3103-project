# Lab 04 Notes — Analytical Star Schema Design in DuckDB

## 1. Objective

This lab focuses on turning the cleaned and merged market-price dataset into a small analytical warehouse using a star schema. The source data is the processed file generated by the earlier ETL pipeline:

- `data/processed/prices_with_rainfall.parquet`

This file contains the columns:

- `id`
- `date`
- `market`
- `commodity`
- `price`
- `rainfall_mm`

The purpose is to create a structure that makes analytical queries simpler, more readable, and easier to scale than querying a flat Parquet file directly.

---

## 2. How the project reached this point

Before Lab 04, the project already followed a standard data pipeline:

1. Source A was ingested from the raw market prices file.
2. Source B was ingested from the rainfall file.
3. The data was cleaned and validated.
4. Invalid rows were rejected or corrected.
5. Price and rainfall data were merged on `date` and `market`.
6. The final processed output was stored as a Parquet file.

This matters because Lab 04 does not create a fresh raw dataset. It uses the finished processed table produced earlier and builds analytics on top of it.

## 3. Step 1 — Baseline query on the flat file

The first task was to run a direct DuckDB query on the flat Parquet dataset. The example query was:

```sql
SELECT market, AVG(price) AS mean_price
FROM 'data/processed/prices_with_rainfall.parquet'
WHERE commodity = 'Maize'
GROUP BY market
ORDER BY mean_price DESC
```

This answered the baseline question:

- Which market has the highest average maize price?

Why this matters:

- It gives a performance baseline for the original file.
- It also shows the raw analytical behavior before we introduce the star schema.

The query was timed using Python's `time.perf_counter()` so we could compare runtime before and after the schema design.

## 4. Step 2 — Designing the star schema

A star schema is used for analytical databases because it separates business dimensions from the central fact table.

### Fact table

`fact_price_observation`

One row per observation, storing measurements for each record.

Suggested columns:

- `id`
- `market_id`
- `commodity_id`
- `date`
- `price`
- `rainfall_mm`

### Dimension tables

`dim_market`

- `market_id`
- `market_name`

`dim_commodity`

- `commodity_id`
- `commodity_name`

### Schema diagram concept

```text
                 +-------------------+
                 | dim_market        |
                 | market_id         |
                 | market_name       |
                 +-------------------+
                            |
                            |
      +-----------------------------------------------+
      | fact_price_observation                       |
      | id, date, market_id, commodity_id, price,   |
      | rainfall_mm                                  |
      +-----------------------------------------------+
                            |
                            |
                 +-------------------+
                 | dim_commodity     |
                 | commodity_id      |
                 | commodity_name    |
                 +-------------------+
```

This design reduces redundancy because the market and commodity names are stored once in the dimension tables, while the fact table stores the numerical and transactional measurements.

Sentence for the assignment:

- “We traded away the simplicity of one flat table for the gain of faster analytical querying, cleaner dimension relationships, and easier reporting.”

---

## 5. Step 3 — Building the schema in DuckDB

The next task was to create the tables in DuckDB and load the data.

### Build the market dimension

```python
dim_market = df[["market"]].drop_duplicates().reset_index(drop=True)
dim_market["market_id"] = dim_market.index
```

This creates a unique list of markets and assigns each a numeric key.

### Build the commodity dimension

```python
dim_commodity = df[["commodity"]].drop_duplicates().reset_index(drop=True)
dim_commodity["commodity_id"] = dim_commodity.index
```

This keeps commodity names normalized and avoids repeated text values in the fact table.

### Build the fact table

The fact table was created by merging the base DataFrame against both dimensions so each row received:

- `market_id`
- `commodity_id`

Then only the important analytical fields were kept:

```python
fact = df.merge(dim_market, on="market").merge(dim_commodity, on="commodity")
fact = fact[["id", "date", "market_id", "commodity_id", "price", "rainfall_mm"]]
```

This is the central analytical table used for all future reporting.

## 6. Step 4 — Five analytical queries

The point of the star schema is that queries become easier to write and read, especially when reporting by business categories such as market and commodity.

### Query 1 — Average price by market

```sql
SELECT dm.market, AVG(f.price) AS mean_price
FROM fact_price_observation f
JOIN dim_market dm ON f.market_id = dm.market_id
GROUP BY dm.market
ORDER BY mean_price DESC
```

This shows how each market compares in terms of average price.

### Query 2 — Observation count by commodity

```sql
SELECT dc.commodity, COUNT(*) AS n_observations
FROM fact_price_observation f
JOIN dim_commodity dc ON f.commodity_id = dc.commodity_id
GROUP BY dc.commodity
ORDER BY n_observations DESC
```

This tells us which commodity has the most records in the dataset.

### Query 3 — Average rainfall by market

```sql
SELECT dm.market, AVG(f.rainfall_mm) AS mean_rainfall
FROM fact_price_observation f
JOIN dim_market dm ON f.market_id = dm.market_id
GROUP BY dm.market
ORDER BY mean_rainfall DESC
```

This links market-level weather conditions to sales observations.

### Query 4 — Maximum price per commodity and market

```sql
SELECT dm.market, dc.commodity, MAX(f.price) AS max_price
FROM fact_price_observation f
JOIN dim_market dm ON f.market_id = dm.market_id
JOIN dim_commodity dc ON f.commodity_id = dc.commodity_id
GROUP BY dm.market, dc.commodity
ORDER BY dm.market, dc.commodity
```

This is useful for identifying the maximum observed price in a category.

### Query 5 — Price and rainfall summary by market and commodity

```sql
SELECT dm.market, dc.commodity, AVG(f.price) AS mean_price,
       AVG(f.rainfall_mm) AS mean_rainfall_mm
FROM fact_price_observation f
JOIN dim_market dm ON f.market_id = dm.market_id
JOIN dim_commodity dc ON f.commodity_id = dc.commodity_id
GROUP BY dm.market, dc.commodity
ORDER BY mean_price DESC
```

This query combines the dimensional information and the fact values into a useful business intelligence view.

## 7. Step 5 — Performance comparison: flat Parquet vs star schema

The next step was to measure the time taken by the same logical query in two different structures:

- flat Parquet query
- star schema query

### Example timing structure in Python

```python
t0 = time.perf_counter()
db.sql("""
    SELECT market, AVG(price)
    FROM 'data/processed/prices_with_rainfall.parquet'
    GROUP BY market
""").df()
flat_time = time.perf_counter() - t0
```

Then the equivalent query against the star schema is timed using:

```python
con = db.connect(DB_PATH)

start = time.perf_counter()
con.sql("""
    SELECT dm.market, AVG(f.price) AS avg_price
    FROM fact_price_observation f
    JOIN dim_market dm ON f.market_id = dm.market_id
    GROUP BY dm.market
""").df()
star_time = time.perf_counter() - start
```

### What to observe

For a small dataset, the difference is often small. The flat file may be just as fast or even faster because the dataset is not large enough to benefit strongly from a denormalized analytical design. The star schema may have a slightly higher overhead because it requires joins between the fact table and dimension tables.

However, the star schema still offers advantages:

- clearer business logic
- easier reporting
- better long-term scalability
- cleaner maintenance for addition of new dimensions or filters

### Interpretation

In this lab, the performance difference is likely small because the dataset is modest. The real benefit is not raw speed alone; it is the analytical design and maintainability of the structure.

## 8. Step 6 — Architecture decision justification

A strong final argument for this lab is:

> For the current dataset size, a star schema is not primarily about giving a huge performance boost; it is about making the table easier to reason about and report on. The flat Parquet file is simpler and may even be faster for a small dataset, but the star schema is more structured, readable, and scalable for future analytics work.

This is a valid conclusion because the data is not huge, so the join overhead is minor. The structure improves data warehouse thinking and makes requirements like market-by-commodity reporting easier to implement cleanly.

## 9. Final understanding

This lab teaches an important data engineering principle:

- Flat files are great for storage and portability.
- Star schemas are better for analytical workloads and reporting.
- The best design depends on both data size and the type of questions you want to answer.

In short, this lab connects the ETL work from earlier in the course to the analytics layer. It shows how cleaned and merged data can be transformed into a structure that supports business reporting and downstream analysis.
